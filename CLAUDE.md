## Architecture

### Stack
Next.js App Router (`src/app`) + TypeScript + Bootstrap 5/React-Bootstrap for layout primitives, with feature-specific styling in CSS Modules. Redux Toolkit (`src/store`) holds only the auth slice; per-feature UI/editor state lives in React Context (`src/context`) instead — don't reach for Redux for new local state.

### Auth: two layers, two identity sources
- **Firebase** (`src/firebase/firebase.ts` client, `firebase-admin.ts` server) is the identity provider. Client-side sign-in exchanges a Firebase ID token for a server session cookie (`AUTH_COOKIE_NAME = "session"`, `src/lib/auth/constants.ts`).
- **`src/middleware.ts`** only checks whether the session cookie is *present* (fast path) against `PROTECTED_ROUTES` in `constants.ts` — it does not verify it. The "already logged in" redirect lives in the login/signup pages, which verify the session for real (a stale cookie must not bounce between login and the dashboard).
- **Session lifetime** (`src/lib/auth/constants.ts`, `src/lib/auth/session.ts`): 30 min idle and 12 h absolute, per OWASP and NIST SP 800-63B AAL2. The cookie lives 30 min and `/api/auth/refresh` extends it only while the current session is still valid; the absolute limit is measured from the original `auth_time`. `/api/auth/login` only accepts a sign-in from the last 5 minutes. On the client, `useSessionTimeout` (mounted by `SessionInitializer`) tracks activity across tabs, renews while active, warns 2 min before and signs out; the live panel counts as activity.
- **Play sessions**: `LUDI_SESION.estado` is read through `sessionPhase` (`src/lib/play/sessionState.ts`). Students wait in `WaitingRoom` until the teacher starts the activity; answer/award/form routes use `authorizeParticipant(..., { requireActive: true })`. Leaving the live panel (`/dashboard/live/[id]`) never ends the session: `useLeaveWarning` asks before leaving while it is open, and `OpenLiveSessions` (dashboard layout, `/api/live/open`) offers "Volver al panel en vivo" for the teacher's sessions still open in the last 24 h.
- Real verification happens per-request in Server Components/Actions via `getSession()` (`src/lib/auth/getSession.ts`, calls `adminAuth.verifySessionCookie`) and `getCurrentUser()` (`getCurrentUser.ts`), which additionally looks up the matching `LudiUser` row in SQL Server by `firebaseUid`. Any server code that needs the app-level user (role, id used for Prisma relations) must call `getCurrentUser()`, not just trust the cookie.
- `src/lib/auth/guards.ts` centralizes authorization: `requireUser`/`requireAdmin` for pages, `isAdmin`, and `canAccessActivity(user, activityId, "owner" | "play")`. Every Server Action and API route that reads or changes an educator's data must check the session user and ownership with these - never trust a user id sent by the client.
- `/api/play/*` has no user session: students join with a PIN and have no account. Instead, `/api/play/join` issues a per-participant secret (only its SHA-256 is stored in `token_hash`); the client sends it via `postPlay` (`src/features/play/playApi.ts`) and every play route checks it with `authorizeParticipant` (`src/lib/play/participantToken.ts`). Participants created before this check have no hash and are allowed through.
- After login, `SignInForm` returns to `?redirect=` through `safeRedirectPath` (`src/lib/auth/redirect.ts`, internal paths only).

### Database: legacy-shaped schema via Prisma
`prisma/schema.prisma` targets SQL Server. Model names are a mix of PascalCase (mapped to `LUDI_*` tables via `@@map`) and raw legacy tables. Two things to know before touching activity data:
- An activity is split across a legacy `ACTIVITY` row and a `LudiActividad` row pointing at it 1:1 — creating an activity means creating both (see `src/services/activityWrite/createActivity.ts`).
- Free-form/experimental settings that don't have their own columns are stashed as JSON in `LudiActividadConfig.ajustesJson` (e.g. voice, background image; badges/missions moved to their own tables) rather than normalized further — check there before adding new columns for editor config.
- Saving lives in `src/services/activityWrite` (`createActivityForUser`, `updateActivityForUser`, run inside `prisma.$transaction`); it takes the session user and must never be exported from a `"use server"` file. The editor's `SaveActivityButton` calls it through `POST /api/activities` and `PUT /api/activities/[id]` (`activityRequest.ts`: same-origin check, session, strict Yup shape). It is the only entry point for saving (see `docs/guardado-de-actividades.md`). Reading for edit is `getActivityForEdit` in `src/app/actions`.

### i18n
`next-intl` with locales `es` (default, unprefixed) and `en`, configured in `src/i18n/routing.ts` and `src/i18n/request.ts`. There is no `[locale]` route segment — routing is unprefixed for the default locale. Translation strings live in `messages/{es,en}.json`, both must be kept in sync when adding a key (`src/lib/i18n/__tests__/messages.test.ts` fails if keys or `{params}` differ). No user-visible text is hard-coded: client components use `useTranslations`, server components/actions/routes use `getTranslations`. Shared logic that runs on both sides (validators, save services) returns a `MessageDescriptor` (`src/lib/i18n/message.ts`) and the caller translates it with `useMessage()` or `translateMessage()`. Activity type names are never translated: LudiQuiz, TrueOrFalse, LudiMemory, LudiLección, LudiForm in every locale. Labels that come from DB rows in Spanish are shown by id instead: grades and activity types via `Common.grades.<id>` / `Common.activityTypes.<id>`, True/False options by `indice`. Dates use `useFormatter`/`getFormatter`. API routes whose `error` reaches the UI answer in the user's language (`Errors`, `AuthErrors`); never send raw DB/Firebase messages to the client.

### SEO and metadata
Every page exports `generateMetadata` built with `pageMetadata()` (`src/lib/seo/metadata.ts`): translated title (the root layout adds " | LudiGame"), description, Open Graph/Twitter and robots. Pages default to `noindex`; only the public ones pass `index: true` and a canonical `path` (also listed in `PUBLIC_PATHS` for `src/app/sitemap.ts`). `src/app/robots.ts` disallows the private areas. Client-component pages (the editors) declare metadata in a sibling `layout.tsx`. Set `NEXT_PUBLIC_SITE_URL` per environment for canonical and Open Graph URLs.

### The activity editor (`/create/*`)
Five activity types share one editor shell: `ludiquiz`, `ludimemory`, `trueorfalse`, `ludileccion`, `ludiform` (`src/app/create/<type>/page.tsx`), wrapped by `src/app/create/layout.tsx` which renders `CreateNavbar` and provides `ActivityEditorProvider`.
- **`ActivityEditorContext`** (`src/context/ActivityEditorContext.tsx`) is the single source of truth for the activity being edited (title, type, background, questions, `GamificationConfig`) — it is per-editor-session client state, reset via `resetEditor()`, not persisted until `SaveActivityButton` sends it to `/api/activities`.
- **`GamificationPanel`** (`src/features/gamification/components/GamificationPanel`) is rendered by every editor through `EditorGamificationColumn`. Its fields depend on the activity type: only LudiQuiz/Verdadero-Falso have a timer, LudiLección has no points, and each type has its own badge/mission catalog. The panel's voice toggle is for students only: the editor never speaks. Students hear `badgeUnlocked` through `useGameVoice`, using the teacher's voice profile (`voiceGender`/`voiceSpeed` in `LudiUserConfig`, set in Settings > Preferences); `pickVoice` in `voiceProfile.ts` maps it to the closest installed voice on the student's device.
- **Badges and missions** are data, not code: the catalog (code, catalog key, `regla`, `umbral`, image) lives in `LUDI_INSIGNIA`/`LUDI_MISION`, seeded from `prisma/seeds/achievementCatalog.ts` (run it alone with `npx ts-node --compiler-options {"module":"CommonJS"} prisma/seeds/runAchievementCatalog.ts`). `getAchievementCatalog()` (`catalog.server.ts`, cached under `ACHIEVEMENT_CATALOG_TAG`) reads it and `AchievementCatalogLoader` provides it to client components in the editor, the student player and the report; read it with `useAchievementCatalog()`. Texts are in `messages` under `Achievements` (badges by code, missions by `catalog.rule` with the threshold as `{value}`) and are read only through `useAchievementText()`. `achievementRules.ts` maps each `regla` to a check; a new mission that reuses an existing rule needs only a DB row. Usage is linked by foreign key: the badges/missions chosen for an activity live in `LUDI_ACTIVIDAD_INSIGNIA`/`LUDI_ACTIVIDAD_MISION` (written by `replaceActivityAchievements`, read via `ACTIVITY_ACHIEVEMENTS_INCLUDE` in `activityAchievements.ts`, not in `ajustesJson`) and earned ones in `LUDI_PARTICIPANTE_INSIGNIA`/`LUDI_PARTICIPANTE_MISION`; `/api/play/award` only accepts what the played activity selected. Retire an achievement with `activo = false` (in-use rows cannot be deleted). Keep `codigo` stable anyway: the `messages` keys use it. The one-off data migration from the old text-coded table is `prisma/sql/2026-10-12_achievement_links.sql` (transactional; aborts on unknown codes).
- Left question-list sidebar, header, and the `GamificationPanel` are "chrome" around a central preview canvas that mimics what the student will see — the canvas is intentionally more saturated/playful than the chrome around it; keep that contrast when touching editor styling.
- Shared editor UI pieces live in `src/components/editor` (barrel-exported via `index.ts`); gamification-specific pieces live in `src/features/gamification`.
- The left column of every list-based editor is built from the kit in `src/components/editor/list` (`EditorSidebar`, `EditorAddButton`, `EditorFooterButton`, `EditorList`/`EditorListItem`, `moveItem`). New editors should compose these instead of styling their own list items, so select/reorder/delete look and behave the same everywhere. `EditorTypePicker` is the shared "add an item of type X" button.
- Block-style editors (LudiLección, LudiForm, LudiMemory) build the center column from `src/components/editor/canvas` (`EditorCanvas`, `EditorCard`, `EditorPlaceholder`, `EditorNotice`, `EditorGamificationColumn`, `editorFieldStyles`). The LudiQuiz/Verdadero-Falso canvas is intentionally left as its own markup.
- **LudiLección** (`src/features/lesson`): a lesson is a sequence of content blocks stored as `LudiPregunta` rows with `esContenido = true` (reading text in `contenidoTexto`, media via `LUDI_PREGUNTA_RECURSO`). Allowed block kinds depend on the grade (`isBlockAllowedForGrade`, enforced in both the editor and the save service). Rewards are completion-based (`evaluateLessonBadges`/`evaluateLessonMissions` in `achievementRules.ts`), not answer-based.
- Content slides/blocks (`esContenido`) are untimed and unscored in `GameEngine`, and `/api/play/submit-answer` rejects them.
- **Answer scoring** (LudiQuiz, Verdadero/Falso): `answerPoints` in `src/lib/play/scoring.ts` is the only formula, used by `/api/play/submit-answer` (authoritative) and `GameEngine` (display). With "Premiar la rapidez" (`GamificationConfig.speedBonus`, stored in `ajustesJson`, missing means `true`) a correct answer is worth between half and all of the question's points depending on time left; without it, exactly the points set. The panel shows both modes as a radio choice (`panel-scoring`, also a step of the LudiQuiz and TrueOrFalse tours) with an example computed by `answerPoints` from the current points and time.
- **LudiForm** (`src/features/form`): third grade only (`isFormAvailableForGrade`, checked in Crear actividad, the editor and the save service). Questions are `LudiPregunta` rows with `tipoPregunta` = `single` | `multiple` | `long`; no timer. Students submit the whole form once via `/api/play/submit-form`, which grades closed questions server-side (`gradeFormAnswer`) and stores long answers as `estadoRevision = PENDIENTE` until the teacher grades them in Reportes (`reviewWrittenAnswer`). Pending answers are excluded from report statistics (`isPendingReview`).
- **LudiMemory** (`src/features/memory`): each image is a `LudiMemoriaPareja` with two `LudiMemoriaTarjeta` (sides A/B). 2-12 images (`validateMemoryForSave`). No timer; `MemoryEngine` shuffles on start and `/api/play/submit-memory` sets the score server-side (pairs x `puntajeBase`) once per participant. Misses only affect badges.
- **Follow-up** (`src/features/followUp`): whether an activity helped meet the class objective. Students answer two optional 1-5 questions in `SummaryActions` (all five types, never in preview, honoring `enableStudentFeedback`) saved by `POST /api/play/feedback` into `studentEnjoyment`/`studentLearning`. Teachers answer `TeacherEvaluationForm` (effectiveness 1-5 naming the grade, objective Sí/Parcialmente/No as `objectiveLevel` 0-2, and difficulty only for template copies) when finishing a live session or later from the report; `POST /api/live/teacher-feedback` is the only save path (owner check). `aggregateFollowUp` consolidates by activity (template copies grouped via `LudiActividad.plantillaOrigenId`) and grade for `/admin/reports`. `objectiveMet`, `classEngagement` and `studentRating` are obsolete columns kept for old data; migration: `prisma/sql/2026-10-13_activity_follow_up.sql`.
- **Guided tours** (driver.js). The only tour offered on its own is **"Crea tu primera actividad"** (`src/features/tours/firstActivity`): an invitation card on `/dashboard` for teachers without activities, then 6 steps from the sidebar to the LudiQuiz editor in the same tab (steps, routes and the per-tab state in `firstActivitySteps.ts`; `FirstActivityTour` is mounted by the `/dashboard` and `/create` layouts). It never blocks the page, waits while any modal/drawer (`aria-modal`, `.modal.show`) is open, skips a step whose `data-tour` element is not visible after 2 s, and finishes when `SaveActivityButton` announces `ludi:activity-saved` (`activitySavedEvent.ts`; the tour cancels it to stay in the editor in edit mode). Its status (`pendiente`/`pospuesta`/`en_progreso`/`completada`) and step live in `LUDI_USER_CONFIG.completed_tours` (`firstActivity` in the JSON) through `/api/user/tours` (not `/api/user/config`, whose omitted fields reset to defaults); read it with `useTourPreferences`. Settings opens it at a step with `?primera-actividad=<n>`. Every step of every tour is shown by `presentTourStep` (`src/features/tours/tourStep.ts`), which owns the shared rules (Salir/Anterior/Siguiente, Esc, no blocking, wait for modals, skip missing elements, outline, focus, mobile card; tooltip styles `.ludi-guide-*` in `globals.css`); a panel that stays mounted while closed must not keep `aria-modal` (make it `inert`). The other tours (`useGuidedTour`; the editors' steps in `src/features/tours/editorTours.ts`, shown by `EditorTour`) only open on request with `?tour=<id>` from Settings > Visitas guiadas (catalog, groups and FAQ in `src/lib/tours/tourRegistry.ts`; a `route: null` tour shows as "Próximamente"). Steps target `data-tour="..."` attributes, never CSS classes. `/welcome-educator` has no tour.
- **Subjects** (`src/features/subjects`): a data catalog like badges (`LUDI_MATERIA`, `LUDI_MATERIA_GRADO`, seeded by `prisma/seeds/subjectCatalog.ts`, texts by `codigo` in `Subjects`); the teacher's picks per grade live in `LUDI_USUARIO_MATERIA` (base for suggesting activities), saved only through `PUT /api/user/subjects`. After choosing a grade for the first time, `WelcomeFlow` (`src/app/welcome-educator`) slides the page to `SubjectStep` instead of opening a modal, once per grade (skipping is recorded as `subjects_grade_<id>` in the tour progress); they are edited in Settings > Preferences. Migration: `prisma/sql/2026-10-14_subject_catalog.sql`. The grade flow itself (asked after login) is unchanged.
- **Templates** (`src/features/templates`): the catalog is versioned content, one JSON file per template in `catalog/templates/<grade>/` plus `catalog/collections.json` (format and per-grade gamification in `catalogSchema.ts`; topics aligned with MINED Nicaragua textbooks but with original text). `node scripts/templates/resolve-media.mjs [--dry-run]` fills pending media (Pixabay is downloaded to Storage `uploads/pixabay_*` because it forbids hotlinking; Unsplash is hotlinked with its download ping and credit; YouTube only embeddable `madeForKids` videos) and regenerates `catalog/index.ts`. An admin loads it with Settings > Administración > Sincronizar plantillas (`syncTemplateCatalog`), which writes each one through `createActivityForUser`/`updateActivityForUser` keyed by `codigo`, skips unchanged ones by content hash and hides removed ones. `LUDI_PLANTILLA` (class, collection, cover) and `LUDI_PLANTILLA_COLECCION` hold what only a template has; they are not `LUDI_TEMA` (background themes). In `/dashboard/templates` (`templates.server.ts`) "Usar plantilla" saves one copy per teacher (`saveTemplateCopy`, reused if it exists); only that copy is editable, and "Lanzar" launches the copy so the session and report are the teacher's. `src/features/templates/__tests__/catalog.test.ts` validates the whole catalog with the editor's save rules. Migration: `prisma/sql/2026-10-15_template_catalog.sql`.
- **Minigames** (`src/features/minigames`): ready-made games with their own styles, stars, sounds and voice; they are not activities (no editor, PIN, session or report). The registry is `minigames.ts`, each game is its own component (picked by `MinigamePlayer`), assets live in `public/minigames/<slug>/`, the gallery is `/dashboard/minijuegos` (sidebar) and the game itself is public at `/play/minijuegos/<slug>` so students open it from a shared link. Texts in `Minigames`; voice picked with `pickVoice` for the locale.
- **Notifications** (`src/features/notifications`): the dashboard bell (`NotificationBell`, in `NavbarDashboard`) lists `LUDI_NOTIFICACION` rows through `/api/notifications` (GET, PATCH to mark read); it polls every minute, no realtime. One row per user and `clave` (e.g. `review:<sessionId>`), so the same fact updates its notification instead of repeating it. Rows are created only server-side in `notifications.server.ts`, right where the fact happens: `syncPendingReviews` after `/api/play/submit-form` and `reviewWrittenAnswer` (LudiForm long answers to grade; removed at 0), `notifySessionFinished` when `/api/live/[id]` ends a session (summary, and the evaluation request unless already rated or `enableTeacherEvaluation` is off), `resolveEvaluation` in `/api/live/teacher-feedback`. These calls never throw: a notification failure must not break the student's or teacher's action. Texts are per type in `Notifications.types.<tipo>` with the row's `datos` as params. Types a teacher turns off live in `LUDI_USER_CONFIG.muted_notifications` (`/api/notifications/preferences`, Settings > Preferences) and are neither created nor listed. Migration: `prisma/sql/2026-10-15_notifications.sql`.
- Players: `ActivityPlayer` (`src/features/play`) picks `FormEngine`, `MemoryEngine` or `GameEngine` by activity type; all share `usePlaySession` (settings, participant, voice, achievements) and `PlayScreens` (background, ready card, achievements recap, summary actions). Use `ActivityPlayer` wherever an activity is played or previewed.

### Styling
Bootstrap utility classes are used for layout (`row`/`col-*`/`d-flex`), CSS Modules for component-specific styling, plus two overlapping design-token sources — know which one is actually live before using either:
- `src/styles/variables.css` (imported globally via `globals.css`) defines a generic `--primary-color`/`--spacing-*`/`--shadow-*` token set used by the reusable `src/styles/components/*.module.css` primitives (Button, Card, etc.) and by the `/create` editor.
- `src/styles/pages/LudiDesign.module.css` is the *actual* brand identity seen across `/dashboard` (deep violet `#6a4bff`/`#140a2e`, cyan accent `#00d4ff`, per-activity-type gradients). New UI in `/dashboard` should match this file's palette, not `variables.css`.
- **Teacher panel type scale** (`variables.css`), required in every sidebar view (`/dashboard/*`, `/admin/*`): `--text-meta` 13px (metadata, dates, labels, column headers; the absolute minimum, no text below it), `--text-ui` 14px (sidebar items, buttons, inputs, selects, table cells), `--text-base` 15px (body text, descriptions), `--text-section` 16px (section titles), `--text-card` 18px (titles inside cards), `--text-title` 26px (page h1). Change sizes only, keep the existing weights and fonts. `src/styles/panelText.module.css` (`.panelText`, applied by `DashboardFrame` and by panel pages outside it such as `/views/activity/[id]`) sets the base size and keeps Bootstrap's `.small`/`.badge` at or above 13px.
- **Editor palette** (`variables.css`, `--c-*`), used by every editor under `/create/*` so its chrome matches the teacher panel: `--c-shell` (top bar), `--c-shell-divider`, `--c-ground` (page background), `--c-shell-control`/`--c-shell-border`/`--c-shell-text`/`--c-shell-muted`/`--c-shell-accent` (controls on the dark bar), `--c-primary`/`--c-primary-hover` (primary action: Guardar, Agregar pregunta), `--c-text`, `--c-muted` (secondary text on white, 4.5:1), `--c-focus-dark`/`--c-focus-light` (focus outline on dark/white). `src/app/create/editorShell.module.css` (applied by `create/layout.tsx`) sets the page background, editor placeholders and `:focus-visible`. The central canvas, the selectable themes, the answers' colors (including the green "correct" marks) and the floating dark Game panel do not use this palette.
- Panel filters, lists and tables share `ActivityFilter.module.css` (search, selects, chips), `ActivityCollection` (list/grid toggle in the filter row, list rows inside one white container with the pagination as its footer) and `src/components/ui/DataTable.module.css` (table container, 40px header, 60px rows).

## Project conventions

- TypeScript strict mode; avoid `any`, prefer early returns and functional style.
- No emojis or decorative symbols in code, comments, or commit messages generated for this repo.
- Comments should be short and explain *why*, not *what* — remove dead/redundant code rather than leaving it commented out.
- Prioritize accessibility (ARIA roles/labels) on interactive/gamified UI — see `SelectableCard`/`QuestionListItem` for the existing `role="button"`/`aria-pressed` pattern used instead of native `<button>` where a custom toggle card is needed.
- API routes should validate input with Yup (`yup` is a dependency) even though not every existing route does this yet — validate new routes rather than following an unvalidated one as precedent.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost). `.graphifyignore` limits the graph to `src`; edit it there instead of passing another path, so the git hooks and manual updates write the same graphify-out/.
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
