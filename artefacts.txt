1. DEFINICION DE HECHO (DoD)
==============================

Criterios obligatorios para considerar una Historia de Usuario como "Done":

[CODIGO Y COMPILACION]
- Codigo compila sin errores: npm run build exitoso en Next.js 16 (App Router)
- TypeScript strict mode sin errores: tsc --noEmit sin warnings
- ESLint sin errores: npm run lint pasa sin violations
- Sin uso de any en codigo nuevo (usar unknown para catch blocks)
- Indentacion de 4 espacios (convencion del proyecto)
- Semicolons obligatorios en todas las sentencias

[TESTING]
- Tests unitarios escritos para logica de negocio critica (Jest + RTL)
- Tests de integracion para API routes (minimo happy path + error cases)
- Todos los tests pasan: npm test sin failures
- Cobertura minima del 70% en modulos nuevos

[BASE DE DATOS]
- Operaciones multi-tabla usan prisma.$transaction() para atomicidad
- Migraciones de schema aplicadas y versionadas en prisma/migrations/
- Queries optimizadas (sin N+1, includes selectivos)
- Validacion de datos en capa de aplicacion (Yup schemas)

[AUTENTICACION Y SEGURIDAD]
- Rutas protegidas verifican sesion via getCurrentUser() o middleware
- API routes retornan 401/403 cuando corresponde
- Validacion de ownership en operaciones de escritura (userId check)
- No exposicion de datos sensibles en cliente (passwordHash, firebaseUid)

[INTERNACIONALIZACION]
- Textos visibles al usuario usan next-intl (useTranslations/getTranslations)
- No strings hardcodeados en componentes nuevos (excepto nombres propios)
- Archivos messages/es.json y messages/en.json actualizados

[ACCESIBILIDAD]
- Componentes interactivos con atributos ARIA (role, aria-label)
- Formularios con labels asociados (htmlFor)
- Navegacion por teclado funcional (tabIndex, onKeyDown)
- Contraste de colores cumple WCAG AA

[RESPONSIVE Y UI]
- Funcional en resoluciones desktop (1920x1080) y tablet (768x1024)
- Bootstrap 5 grid system usado correctamente
- Mobile-first approach en componentes nuevos
- Estados de carga, error y vacio implementados

[GAMIFICACION (para historias con enfoque ludico)]
- Elementos ludicos configurables desde Panel Ludico
- Feedback auditivo con Web Speech API cuando voiceEnabled=true
- Animaciones de confetti en interacciones clave
- Puntos calculados con formula de velocidad (si aplica)

[DEPLOYMENT]
- GitHub Actions pipeline pasa sin errores (build + deploy a Azure)
- Variables de entorno documentadas en .env.example
- Sin secretos commiteados al repositorio

[DOCUMENTACION]
- Comentarios en espanol explicando el "por que" (no el "que")
- README actualizado si hay cambios arquitectonicos
- API routes documentadas con JSDoc (params, response schema)

[CODE REVIEW]
- Pull Request aprobado por al menos 1 reviewer
- Sin comentarios de "resolve before merge"
- Convenciones de nombre seguidas (PascalCase componentes, camelCase funciones)

2. SPRINT GOAL SUGERIDO
==============================

SPRINT ACTUAL (Sprint N):
"Completar internacionalizacion y estabilizar nomenclatura de sesiones"

JUSTIFICACION:
El analisis de ingenieria inversa revela que el producto esta funcionalmente 
completo (89 de 90 historias en estado Done). Sin embargo, existen dos areas 
de deuda tecnica critica que impactan la mantenibilidad y experiencia de usuario:

1. Internacionalizacion incompleta (HU-085): Multiples paginas del dashboard, 
   reportes y panel ludico tienen textos hardcodeados en espanol, rompiendo 
   la promesa de soporte bilingue.

2. Inconsistencia de estados de sesion: Los valores de estado en LUDI_SESION 
   usan multiples convenciones ("ESPERANDO", "lobby", "activa", "ACTIVA", 
   "finalizada", "FINALIZADA"), generando bugs de filtrado en reportes.

HISTORIAS CANDIDATAS PARA ESTE SPRINT:
- HU-085 (Completar i18n en dashboard, reportes, panel ludico)
- Refactor: Normalizar estados de sesion a enum consistente
- Refactor: Migrar misiones e insignias hardcodeadas a base de datos
- Refactor: Eliminar uso de any en APIs y Server Actions

CAPACIDAD SUGERIDA: 40-50 Story Points (pendiente estimacion Fibonacci)

==============================
3. DEUDA TECNICA IDENTIFICADA
==============================

[CRITICA - Alta Severidad]

DT-01: Estados de sesion inconsistentes
  - Descripcion: LUDI_SESION.estado usa strings inconsistentes: "ESPERANDO", 
    "lobby", "activa", "ACTIVA", "finalizada", "FINALIZADA"
  - Impacto: Bugs en filtrado de reportes, logica de negocio confusa
  - Historias afectadas: HU-061, HU-062, HU-063, HU-077
  - Solucion: Crear enum SessionState en TypeScript y migrar datos existentes
  - Estimacion: 8 puntos

DT-02: (prisma as any) en multiples APIs
  - Descripcion: Uso de (prisma as any) para acceder a modelos con nombres 
    en mayusculas (LUDI_SESION, LUDI_SESION_PARTICIPANTE)
  - Impacto: Perdida de type safety, errores en runtime no detectados en compile
  - Archivos: sessionActions.ts, play/join/route.ts, play/submit-answer/route.ts, 
    play/finish/route.ts, live/[id]/route.ts, play/student/[id]/page.tsx
  - Solucion: Usar @@map en schema.prisma para normalizar nombres de modelos
  - Estimacion: 13 puntos

DT-03: Puntaje calculado solo en cliente
  - Descripcion: GameEngine.tsx calcula puntaje con formula de velocidad 
    (basePoints * (0.5 + 0.5 * timeFactor)) y lo envia al servidor sin validacion
  - Impacto: Vulnerabilidad de seguridad - estudiante puede manipular puntaje
  - Historia afectada: HU-071
  - Solucion: Validar y recalcular puntaje en servidor (submit-answer route)
  - Estimacion: 5 puntos

DT-04: Convencion id > 100 para distinguir registros
  - Descripcion: updateActivity.ts usa id > 100 para distinguir registros 
    existentes de nuevos (IDs temporales del cliente)
  - Impacto: Fragil, depende de que IDs de DB sean siempre > 100
  - Historia afectada: HU-030
  - Solucion: Usar UUIDs temporales en cliente o flag isTemporary
  - Estimacion: 8 puntos

[MEDIA - Severidad Media]

DT-05: Misiones e insignias hardcodeadas
  - Descripcion: MISIONES_POR_GRADO e INSIGNIAS estan hardcodeadas en 
    GamificationPanel.tsx en lugar de venir de base de datos
  - Impacto: Dificil mantenimiento, no escalable
  - Historia afectada: HU-050, HU-051
  - Solucion: Crear tablas LUDI_MISION y LUDI_INSIGNIA en schema.prisma
  - Estimacion: 13 puntos

DT-06: Textos hardcodeados en espanol
  - Descripcion: Dashboard, reportes, panel ludico tienen strings en espanol 
    sin usar next-intl
  - Impacto: HU-085 no puede completarse, soporte bilingue incompleto
  - Historias afectadas: HU-085, HU-011, HU-077, HU-078
  - Solucion: Extraer todos los strings a messages/es.json y usar useTranslations
  - Estimacion: 21 puntos

DT-07: Uso extensivo de any en catch blocks
  - Descripcion: catch (error: any) en multiples archivos en lugar de unknown
  - Impacto: Perdida de type safety, viola convencion de proyecto
  - Archivos: authService.ts, saveActivity.ts, updateActivity.ts, 
    getActivityForEdit.ts, play/join/route.ts, play/submit-answer/route.ts
  - Solucion: Cambiar a catch (error: unknown) y usar type guards
  - Estimacion: 5 puntos

DT-08: Verificacion de admin con rolId === 1 hardcodeado
  - Descripcion: AdminUsers.tsx y admin/users/route.ts verifican admin con 
    rolId === 1 en lugar de usar constante o enum
  - Impacto: Fragil si cambia el ID del rol admin
  - Historia afectada: HU-088
  - Solucion: Crear enum UserRole { ADMIN = 1, EDUCADOR = 2 } y usar constante
  - Estimacion: 3 puntos

[BAJA - Severidad Baja]

DT-09: Dos endpoints de teacher feedback con logica duplicada
  - Descripcion: /api/play/teacher-feedback y /api/live/teacher-feedback 
    tienen logica similar pero diferente schema
  - Impacto: Duplicacion de codigo, confusion
  - Historia afectada: HU-064, HU-076
  - Solucion: Unificar en un solo endpoint con schema flexible
  - Estimacion: 5 puntos

DT-10: No hay expiracion automatica de sesiones en lobby
  - Descripcion: Sesiones en estado "lobby" no expiran automaticamente
  - Impacto: Sesiones huerfanas acumulan en base de datos
  - Historia afectada: HU-061
  - Solucion: Cron job que marque como "expirada" sesiones > 2 horas en lobby
  - Estimacion: 5 puntos

DT-11: Preview button en editor no implementado
  - Descripcion: CreateNavbar.tsx tiene boton de preview (FaEye) pero no 
    tiene handler implementado
  - Impacto: Funcionalidad faltante, UX incompleta
  - Historia afectada: HU-028 (relacionada)
  - Solucion: Implementar modal de preview o nueva pestana con vista de actividad
  - Estimacion: 8 puntos

DT-12: AuthProvider y ReduxProvider duplicados
  - Descripcion: Ambos componentes hacen lo mismo (wrap con Redux Provider)
  - Impacto: Confusion, codigo duplicado
  - Archivos: src/components/providers/AuthProvider.tsx, ReduxProvider.tsx
  - Solucion: Eliminar AuthProvider, usar solo ReduxProvider
  - Estimacion: 2 puntos

==============================
4. RIESGOS IDENTIFICADOS
==============================

[RIESGO-01: Migracion de estados de sesion]
  - Probabilidad: Media
  - Impacto: Alto
  - Descripcion: La normalizacion de estados de sesion (DT-01) puede romper 
    sesiones activas en produccion si no se ejecuta correctamente
  - Mitigacion: 
    * Ejecutar migracion en ventana de mantenimiento (fuera de horario escolar)
    * Script SQL con rollback plan
    * Backup de base de datos antes de migracion
    * Testing en staging environment primero

[RIESGO-02: Internacionalizacion masiva]
  - Probabilidad: Alta
  - Impacto: Medio
  - Descripcion: Extraer todos los strings hardcodeados (DT-06) es tedioso y 
    propenso a errores, puede introducir bugs de renderizado
  - Mitigacion:
    * Dividir en 3 sub-tareas: dashboard, reportes, panel ludico
    * Testing manual en ambos idiomas despues de cada sub-tarea
    * Code review enfocado en verificar keys de traduccion
    * No cambiar logica de negocio, solo extraer strings

[RIESGO-03: Refactor de prisma as any]
  - Probabilidad: Media
  - Impacto: Alto
  - Descripcion: Cambiar @@map en schema.prisma (DT-02) requiere regenerar 
    cliente de Prisma y puede romper queries existentes
  - Mitigacion:
    * Crear rama especifica para este refactor
    * Regenerar prisma client y ejecutar todos los tests
    * Testing manual de flujos criticos (crear actividad, jugar, reportes)
    * Rollback plan: revertir schema.prisma y regenerar client

[RIESGO-04: Validacion de puntaje en servidor]
  - Probabilidad: Baja
  - Impacto: Alto
  - Descripcion: Implementar validacion de puntaje (DT-03) puede cambiar la 
    formula de calculo y afectar puntajes historicos
  - Mitigacion:
    * Mantener formula actual en servidor (no cambiar logica)
    * Solo validar que puntaje enviado <= maximo teorico
    * Log de advertencia si puntaje excede maximo (no rechazar)
    * Monitorear logs despues de deploy

[RIESGO-05: Migracion de misiones/insignias a DB]
  - Probabilidad: Media
  - Impacto: Medio
  - Descripcion: Crear tablas nuevas (DT-05) y migrar datos hardcodeados puede 
    romper el Panel Ludico si no se mapean correctamente
  - Mitigacion:
    * Seed script con datos actuales (mismos IDs y textos)
    * Fallback a datos hardcodeados si query falla
    * Testing manual del Panel Ludico con todos los grados
    * Verificar que voz y confetti siguen funcionando

9. CEREMONIAS SCRUM SUGERIDAS
==============================

[DAILY SCRUM]
- Frecuencia: Diario (Lunes a Viernes)
- Duracion: 15 minutos maximo
- Hora sugerida: 9:00 AM (inicio de jornada)
- Formato: Cada miembro responde 3 preguntas:
  1. Que hice ayer para avanzar el Sprint Goal?
  2. Que hare hoy para avanzar el Sprint Goal?
  3. Hay algun impedimento que me bloquee?
- Lugar: Stand-up virtual (Zoom/Teams) o presencial

[SPRINT PLANNING]
- Frecuencia: Primer dia del sprint (cada 3 semanas)
- Duracion: 4 horas
- Participantes: PO + Equipo de Desarrollo + Scrum Master
- Agenda:
  1. PO presenta Sprint Goal y historias priorizadas (30 min)
  2. Equipo hace preguntas y clarifica dudas (30 min)
  3. Estimacion con Planning Poker (Fibonacci) (2 horas)
  4. Equipo selecciona historias para el sprint (30 min)
  5. Definicion de tareas tecnicas por historia (30 min)
- Output: Sprint Backlog con historias estimadas y tareas

[SPRINT REVIEW]
- Frecuencia: Ultimo dia del sprint (cada 3 semanas)
- Duracion: 2 horas
- Participantes: PO + Equipo + Stakeholders (St. Mary, UNI)
- Agenda:
  1. Demo de funcionalidades completadas (45 min)
  2. Feedback de stakeholders (30 min)
  3. Revision de metricas del sprint (15 min)
  4. Discusion de proximos pasos (30 min)
- Output: Feedback documentado, ajustes al Product Backlog

[SPRINT RETROSPECTIVE]
- Frecuencia: Ultimo dia del sprint (despues de Review)
- Duracion: 1.5 horas
- Participantes: Equipo de Desarrollo + Scrum Master (PO opcional)
- Agenda:
  1. Que hicimos bien? (15 min)
  2. Que podemos mejorar? (15 min)
  3. Acciones concretas para el proximo sprint (30 min)
  4. Review de acciones del sprint anterior (15 min)
  5. Agradecimientos y cierre (15 min)
- Output: 3-5 acciones de mejora con responsables y deadlines

[BACKLOG REFINEMENT]
- Frecuencia: Mitad del sprint (semana 2)
- Duracion: 2 horas
- Participantes: PO + Equipo de Desarrollo
- Agenda:
  1. Review de historias del proximo sprint (45 min)
  2. Clarificacion de criterios de aceptacion (30 min)
  3. Pre-estimacion con T-shirt sizes (S/M/L/XL) (30 min)
  4. Identificacion de dependencias y riesgos (15 min)
- Output: Historias refinadas y listas para proximo Planning
